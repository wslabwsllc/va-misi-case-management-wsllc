# 0018. Veteran Service History: separate mock, shared client transport, outcome stored with the case

* Status: accepted
* Owner: E4 (data model reviewed by E2, UI treatment by E5)
* Extends: [0008](0008-veteran-lookup-mock-and-client.md) (shared client transport, second mock)

## Context

Common Requirement Change 2 ("Additional Data Source", `docs/change-request-plan.md` 0.1) adds a read-only Veteran
Service History Service, `POST /veterans/service-history/lookup`, keyed by the same synthetic SSN as the Veteran Lookup
Service. It answers 200 with branch, service start and end dates and character of service, 404 when there is no record
and 503 when it is temporarily unavailable. The requirement also names "date the source record was last verified",
which the sample 200 omits.

After a successful Veteran Lookup the application must try the new service with the same SSN (R-CR2-1), associate the
result with the case and show it on the case detail (R-CR2-2, R-CR2-3). The Lookup stays the source for name and address
and the new service for service history (R-CR2-4). A no-record answer or an outage must never prevent case creation or
processing, and the user must be told the result (R-CR2-5, R-CR2-6). A local, deterministic mock with synthetic data is
required (R-CR2-7). The Government specifies the outcome, not the architecture, data model, UI or failure handling.

Existing constraints carry over: the SSN is never stored (only its last four digits, A8), no log carries an SSN or
veteran details (ADR 0003, 0008), and an outage of a lookup service must not stop intake (ADR 0008).

## Decision

The decisions are D1 to D9 of the change plan (0.3).

**Separate service (D1).** `src/CaseIntake.VeteranHistory.Mock` runs in its own `veteran-history` container on port 8082,
not published to the host. It is a cut-down copy of the Lookup mock (`HistoryMockProgram`, slim builder, operation
context, problem details, source-generated JSON) and references neither the Lookup mock nor any feature module. Its
synthetic dataset (`Data/service-history.json`, embedded) is generated by `ServiceHistoryDatasetGenerator` with its own
seed from the Lookup's veterans, so every SSN is in area 900-999 and `veterans.json` is unchanged. Demo SSNs:
`900-12-3456` Found (the Government example), `902-17-3062` 404, `962-91-6025` 503 by constant
(`ServiceHistoryDataset.OutageSsn`), so the outage path can be shown without stopping a container. A blank or unreadable
`ssn` is a 400 problem+json and a non-JSON content type a 415 (extensions, as D11 and D12 are for the Lookup). It logs only outcome and duration (event 4060).

**Contract.** `docs/contracts/veteran-service-history.openapi.yaml` is the team's own document. It restates the
Government's interface table and marks the 400 and 415 responses and `lastVerifiedDate` with `x-extension`. The Government
supplied no OpenAPI file for this service, so there is no pinned-hash conformance test as there is for the Lookup;
`HistoryMockServiceTests` exercises every documented response instead.

**Shared client transport.** `VeteranServiceHistoryClient` (`IVeteranServiceHistoryClient`, in
`CaseIntake.VeteranLookup.Client`) uses the same transport as the Lookup client: `LookupTransport.PostAsync` owns the
5 s total budget (so it covers reading the body), the POST, and the mapping of transport failures to `Unavailable`; only
the response mapping differs. Both clients read at most 64 KiB of response (`VeteranLookupModule.MaxResponseBytes`); a
larger body is `Unavailable` whatever the status, so an oversized 404 is `Unavailable`, not `NotFound`. Both typed clients are registered by one factory (`AddLookupServiceClient` in
`VeteranLookupModule`) with the same options shape (`VeteranHistory` section: `BaseUrl`, `AttemptTimeout`,
`TotalTimeout`, `RetryDelay`, validated on start) and the same pipeline (one retry, 2 s per attempt), named
`veteran-history`. The client checks, in order: `veteran.lookup` permission, SSN format (`VeteranLookupClient.Normalize`),
then the call. A 200 is `Found` only when its body passes `CaseTextRules.ValidateServiceHistory`, the same rule intake
applies, so anything the client returns can be stored. Events 4010-4013 log outcome, duration, status and exception type
only.

**Fetched only at lookup time (D2).** The New case page calls the history client in the Lookup's `Found` branch, with the
same SSN, before the SSN is cleared. A throwing client becomes `Unavailable` and logs event 5014. Once the case exists
nothing can query the service again, because the SSN is not stored.

**The case stores the outcome, not just the data (D3).** `Case.ServiceHistoryStatus` is nullable `Found`, `NotFound` or
`Unavailable`; null means the history was not requested (cases created before this change, or a caller that omits it).
The detail page can therefore tell "no record", "the service was down" and "not requested" apart.

**Flat nullable columns on `Cases` (D4)**, next to `VeteranName`, `VeteranAddress` and `VeteranSsnLast4`: status, branch,
start, end, character of service and last verified. Check constraints (`CK_Case_ServiceHistory_*`) back up the domain's
structural rules: a valid status, a status only with a veteran, `Found` with branch, start and character and any other
status with none, and start not after end. The text rules (not blank, no control characters) are enforced by the domain
only; the column lengths (50, 100) cap the size in both.

**No new permission (D5).** The lookup is governed by `veteran.lookup`; every role that creates cases holds it (C1-3).
The stored history is case data, shown to anyone with `cases.view`.

**Reuse `VeteranLookupOutcome` (D6).** Anything other than `Found` or `NotFound` is stored as `Unavailable`.
`InvalidInput` cannot follow a successful Lookup, because the same SSN passed the same format check. `Forbidden` can
follow only if `veteran.lookup` is removed from the user's role between the two calls (permissions are read from the
database on each call, ADR 0013); that rare case is stored as `Unavailable`, which is accepted.

**Optional `serviceEndDate` and `lastVerifiedDate` (D7).** An open end date is someone still serving; the detail shows
"Present". A missing last-verified date shows "Not provided".

**No readiness dependency (D8).** The service has no health check in `/health/ready`, and `web` and `web-e2e` depend on
it with `service_started`, not `service_healthy`. Only the `tests` service waits for it to be healthy, because its tests
call it.

**Free-text branch and character of service (D9)**, capped at 50 and 100 characters. The new service is the authority,
so the application does not reject values it does not know.

## Alternatives considered

- **Add the endpoint to the Lookup mock's container.** Less code and one fewer image, but the two services could not fail
  independently, so `docker compose stop` could not demonstrate an outage, and the Lookup mock serves a pinned
  Government contract that should not change.
- **Fetch history later, on demand from the case detail, or in a background job.** Would allow refreshing a failed
  result, but needs the full SSN after intake, which the application never stores (A8).
- **A separate `ServiceHistories` table.** Would allow several snapshots per case, which nothing needs; one snapshot is
  taken at intake. Flat columns follow the existing veteran-snapshot pattern and keep reads a single row.
- **Store the data only (no status).** Cannot tell "no record" from "service down" from "not requested", which the
  requirement to communicate the result needs.
- **A new `veteran.history` permission.** Changes the golden role matrix and the Roles page for no gain, because every
  case creator must hold both permissions anyway.
- **A readiness check for the new service.** An outage would mark the app unhealthy or block startup, contradicting
  R-CR2-5.
- **Enums for branch and character of service.** Would reject an unknown value from the authoritative source, turning
  valid data into `Unavailable`.
- **A second client copied from the Lookup client.** Faster to write, but would duplicate the budget, error mapping and
  pipeline, which then drift. Moving the Lookup client onto the shared transport did not change its behaviour (its
  existing tests passed without edits). The later 64 KiB response cap is a deliberate change to both clients, with
  its own tests.

## Tradeoffs

- One more image and container to build, scan and run, in exchange for an independent failure and a real outage demo.
- An intake lookup can now wait up to about 10 s (two 5 s budgets in sequence) when both services stall. The form
  stays `aria-busy` and the state is announced throughout.
- The contract is our own document, so it can drift from a future Government definition without a test noticing.
- A user with `veteran.lookup` now sees service history as well as name and address for any SSN they look up. As for
  the Lookup, there is no per-user rate limit and the client events record outcomes, not which veteran was looked up.
- The client and mock reuse the Lookup's naming and project, so "lookup" names cover both services
  (`CaseIntake.VeteranLookup.Client`, `LookupLog`).

## Consequences

- An outage of `veteran-history`, or a 404, never blocks startup, readiness, case creation or case processing; the case
  is created with `Unavailable` or `NotFound` and says so on its detail.
- Service history is never refreshed. An `Unavailable` result is permanent for that case; the user can retry only by
  looking the veteran up again before submitting.
- Cases created before this change keep working. One with a veteran shows "Not requested for this case."; the seeded
  cases have no veteran, so they show no service-history section.
- No SSN, history value, name or address appears in events 4010-4013, 4060 or 5014, or in audit rows (the Created entry
  records only the history status); this is asserted on success and failure paths.
- Mock tests run against the in-process mock and, inside `docker compose run --rm tests`, against the
  `veteran-history` container.
